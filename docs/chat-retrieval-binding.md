# 聊天检索的库层绑定

#9/#22 的部分接线：库调用方可显式设置 `buildApp({ chatRetrievalBinding })`，配置格式与
[手动召回绑定](recall-retrieval-binding.md) 相同：仅包含 fusion 和 rerankerProvider。
复用同一解析器，启动前复制冻结，要求 DB、32字节主密钥和显式持久日配额。
非法配置沿用共享解析器的固定 `INVALID_RECALL_BINDING` 错误，不回显输入。

JSON 和 SSE 都在共用的 prepareAnswer 检索阶段使用绑定。模型回答和后台写回不接收融合或
Provider 选择覆盖；HTTP 消息仍只接受原有正文/附件字段，不能控制开关、精排来源或阈值。
每次检索按持久开关冻结一次有效快照。Score 与聊天调用分别经过日配额准入和用量记录，归属
同一物理 conversation；向模型注入入选记忆，回答的 memories 仍仅保存版本 ID。
关闭精排仍运行配置的融合；增强传输失败回退；配置缺失/损坏沿用检索失败→无记忆回答。
因此“回答成功”不证明精排成功、没有计费或后台记忆提取完成。配额耗尽也可能使后续聊天调用
失败；本轮没有改错误模型、写回、流取消或重试语义。

这是显式库组装入口，官方 index.ts 未设置，无新环境变量，没有修改默认开关或解锁管理 API。
未绑定消费者仍 fail-closed：直接在实验库开启全局 reranker 开关，也不会给旧后台提取消费者
授权。本轮不宣称正式对话写回闭环已支持该全局配置；生产开关解锁前须统一处理消费者能力。
省略新选项时保持既有路径。没有真实 Provider 推理、计费或质量/消融评测；#9/#22 保持打开。

验证用自建随机隔离库、临时本地 Score HTTP 服务及离线聊天模型，覆盖真实 JSON/SSE请求、
入选记忆顺序、持久引用、物理会话用量、关闭/回退/无记忆降级及配置捕获。回滚移除组装选项，
无迁移可回滚。本轮不改变公开请求/响应结构或给客户端增加 Provider Key。
