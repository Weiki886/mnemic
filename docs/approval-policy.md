## 范围与取舍

本 PR 不增加这类能力，也不改变现有聊天、记忆删除或配置命令。**`Refs #34`，不能关闭 Issue。**

- **本轮 1/3**：`@mnemic/shared/approval` 严格契约；CLI 的 `evaluateApproval(context, operation)`；
  三模式决策、可复用规则匹配和真实文件系统路径边界测试。
- **后续 2/3**：启动参数、会话内模式切换与确认交互、单次审批消费、会话/永久授权存储与撤销。
- **后续 3/3**：复用现有 `audit_log` 表/写入能力，记录与查询审批决策，补齐跨端接线验收。
  实际文件/命令 Tools 仍归 #26/#30。以上后续能力均未由本 PR 验收。

备选是一次接入所有层，或先用字符串前缀做宽松路径白名单。本轮选择可独立验证的策略基座，
并用 Node 原生路径/文件系统能力，不引入权限库或第二份配置源。
相对于 Issue 目标中宽泛的“文件写入免确认”，采用 owner 确认的更严格解释：**自动仅免新建确认，不免覆盖确认**。
目录外操作保守拒绝；需要其他目录时，由后续可信控制器明确选择另一项目根，而不是扩大通配授权。

## 权限矩阵（规范）

上下文必须来自可信本地控制器，不能把模型输出或 HTTP 请求中的 `mode/grants/root` 直接当作可信配置。
缺省模式 `read-only`；空串、null、未知模式都拒绝，不回退为 auto。

| 项目目录内的操作                 | read-only | confirm               | auto     |
| -------------------------------- | --------- | --------------------- | -------- |
| 读取普通文件                     | allow     | allow                 | allow    |
| 新建文件，目标不存在且父目录存在 | deny      | ask，或命中可复用规则 | allow    |
| 覆盖已有文件                     | deny      | 每次 ask              | 每次 ask |
| 删除文件/子目录                  | deny      | 每次 ask              | 每次 ask |
| shell，工作目录在项目内          | deny      | 每次 ask              | 每次 ask |

`ask` **不代表允许**；它只告诉后续交互层需要明确的人类确认。本轮没有“确认=true 即执行”的接口。
危险操作的 `allowed_scopes` 仅 `once`。新建可提供 `once/session/permanent`；
可复用 grant 的操作只能是 `file.create`，不接受 once、覆盖、删除或 shell 规则。

例如：auto 评估 `file.create: src/new.ts` 为 allow；同一路径已存在时，评估结果改为
`file.overwrite + ask + [once]`，即使命中过去的新建授权也不能覆盖。
read-only 下给出既存授权，仍然 deny；不是“有授权就覆盖当前模式”。

## 契约与授权匹配

入口：`packages/shared/src/approval.ts`，运行时子入口 `@mnemic/shared/approval`，不在 root 引入运行时解析器。

- context：`project_id/session_id` UUID、绝对 `root`、可选 `mode`、可选 `grants`（最多 1000 条）。
- operation：`kind` 为 file.read/create/overwrite/delete 时携带 `target`；shell 携带 `cwd/command`。
  不接收文件内容、confirm、bypass 等多余字段；路径不接受控制符或双向控制符。
- grant：`project_id/root/target/operation/scope`，session 规则还须 `session_id`；permanent 不携带 session。
  **permanent 是规则的生命周期分类，本轮只定义与匹配该格式，没有落盘或声称重启可恢复。**
- result：`allow/deny/ask` 与稳定原因；成功路径只带实际操作类别及规范化路径，ask 另带允许的授权粒度。
  不回显原始 shell 文本、文件内容或文件系统错误。契约拒绝“auto 放行 shell”之类自相矛盾的结果。

匹配使用**操作 + 项目 UUID + 规范化项目根 + 规范化目标的精确相等**，session 还须会话 UUID 相等。
不做前缀、目录递归、glob 或命令前缀授权；规则必须由后续可信授权层使用 canonical 路径创建。
一个项目的新建授权不能迁移到同路径的另一项目，也不能迁移到同名但不同真实根目录。

本轮评估器不保存状态，也不接收人类确认：没有可复用规则时，重复评估仍然 ask。
**这不是已经完成“单次授权消费/会话存储/永久持久化”验收的证明**，这部分需后续真实交互和存储测试。

## 路径与执行边界

评估器位于 `apps/cli/src/approval-policy.ts`，只读取文件系统元数据，不读文件正文、不写目标、不执行命令。
使用 Node 原生 `resolve/relative`、`lstat/realpath/stat`：先规范化路径，再解析真实目标与父目录；
用路径分量而不是字符串 startsWith 检查项目边界。参考 [Node 22 文件系统文档](https://nodejs.org/docs/latest-v22.x/api/fs.html#fspromisesrealpathpath-options)。

- 根须为已有绝对目录；拒绝文件系统根，允许显式选择的项目目录别名，比较其真实根。
- 新建只允许缺失的最终文件名，父目录须存在且位于真实项目根内；不自动创建祖先目录。
- 已有目标解析符号链接后再检查归属；外链、前缀相同的兄弟目录、坏链接和链接环均不能自动放行。
  有效内链指向已有文件时，也按已有文件处理，不因请求写了 create 而降级为新建。
  解析后的真实根和目标也重新校验路径格式，不能用普通名字的链接绕过控制字符限制。
- 普通读取/覆盖只适用于普通文件；删除可针对文件或子目录，但不能针对项目根本身。
  缺失的读取/覆盖/删除目标不会被静默改成新建；无法解析或校验时 fail closed。

**重要限制：allow 是评估当时的快照，不是可重放的执行凭证，也不是 OS sandbox。**
本轮没有解决检查与操作之间的 TOCTOU；也不限制命令本身能访问哪里，shell 永不自动放行。
后续执行器必须绑定批准的操作与 canonical 路径（不能退回执行原始路径），在实际系统调用处重新核验，
新建采用独占创建，并根据平台使用 no-follow/文件身份校验等措施；路径/文件类型变化时重新审批。
不能仅凭这次评估结果就接一个通用文件写入器或 shell 执行器。
